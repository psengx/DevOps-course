# KT2-03

## Файлы изменений

`compose.student.yaml` - за основу взят `compose.yaml`, изменения ниже:

```yaml
services:
  api:
    image: devops-student:v1
    ...
  web:
    image: devops-student-v1
    ...
```

## Выполненные команды

1. `cp compose.yaml compose.student.yaml` - копия compose-файла
2. `nano compose.student.yaml` и в нано изменение image с `devops-course:base` на `devops-student:v1`
3. `docker compose stop` - остановка основного стенда
4. `docker compose -f compose.student.yaml config` - проверка конфигурации нового compose-файла
5. `docker compose -f compose.student.yaml up -d` - запуск контейнеров в фоновом режиме
6. `docker compose up -d --no-deps --force-recreate api` - пересоздание сервиса api без затрагивания зависимостей

## Наблюдения

1. После выполнения 3 команды все контейнеры старого стенда получили статус `Exited`
2. Команда 4 подтвердив использование указанного в задании образа `devops-student:v1` для сервисов `api` и `web`
3. При первом `up -d` Docker использовал локальный образ `devops-student:v1` и запустил изменённые сервисы. Первая заявка (№15) создалась и отобразилась в системе
4. При выполнении `up -d --no-deps --force-recreate api` был пересоздан **только** контейнер `api`
5. После готовности `api` старая заявка №15 **осталась доступна**, данные не пропали. Новая заявка (№16) успешно создалась

## Потопали по критериям и проверке понимания

#### API_URL и внутренняя сеть:

Переменная `API_URL` внутри контейнера `web` указывает на имя сервиса `api` во внутренней Docker-сети `http://api:8000`. Благодаря встроенному DNS-серверу Docker, контейнеры в одной сети могут общаться друг с другом по именам сервисов, а не по динамическим IP-адресам.

#### Порты: 

Порты (например, `80:80` для `web`) нужны, чтобы приложение было доступно снаружи, через браузер. Внутренние порты наружу не публикуются, они доступны только внутри докера.

#### Том (Volume): 

Для сервиса `api` настроен именованный том `requests`, который монтируется в `/data` (путь задан через переменную `DATA_DIR: /data`). Именно этот том отвечает за постоянное хранение созданных заявок без потери при перезапуске или удалении контейнера.

#### Старая заявка сохранилась: 

При выполнении команды `up -d --no-deps --force-recreate api` старая заявка **не пропала**, так как её файл физически записан на том `requests`. Жизненный цикл этого тома не зависит от самого контейнера `api`

#### Проверка понимания

**Почему нельзя хранить базу только в изменяемом слое контейнера?**

Файлы базы данных нельзя оставлять только в изменяемом слое контейнера, потому что этот слой живет только пока жив конкретный контейнер, и как только контейнер удаляется, удаляется и его изменяемый слой. Без использования внешнего тома `requests` все ранее созданные заявки были бы просто удалены при первом же обновлении `api`.

А ещё любая запись в изменямый слой контейнера проходит через драйвер хранения докера по принципу копирования при записи. Для БД или частых операций с диском это сильно нагружает процессор и сам диск, поэтому использование томов тут выгодная штука - оно позволяет писать данные напрямую в файловую систему хоста.
